# 口袋公园共建养护与开放治理

贯通口袋公园资产、共建责任、巡检维修、开放状态和资金履约。把边角地改造的小微公共空间，
从“多个台账各自为政、居民报修找不到接单方”，收敛为一套带生效区间、可回溯、跨停机一致的
共建养护服务。

## 参与方与事实

主要参与方包括街道管理人员、园林养护人员、共建企业、社区工作人员、居民。领域资料记录以下已经确认的事实：

- 山东利用拆违腾退用地、边角地和闲置地建设口袋公园
- 部分公园配置城市驿站、儿童设施、健身器材、照明及智慧设备
- 政企共建项目采用场地共建、养护共管、资源共享、成果共有机制

## 服务能力

代码分两层：`src/park_store.py`（SQLite 存储与事务发件箱）与 `src/park_service.py`（领域服务）。

| 需求 | 实现方式 |
| --- | --- |
| 地块权属与移交、建设资金、设施资产、适用人群、巡检标准、养护责任、企业承诺、开放时段 | 统一存入 `record_version`，半开生效区间 `[valid_from, valid_to)`，版本只增；支持当日与历史 as-of 查询 |
| 儿童设施/无障碍通道/夜间照明不同检查周期 | 巡检标准按设施专用→设施类别两级匹配（如 7/3/1 天），每日先算应检、扫逾期，停机漏跑一次性补算 |
| 逾期责任可追溯 | 任务在生成时快照责任方，并按“应检当日”生效的责任版本解析；移交不改旧账 |
| 巡检现场证据 | 证据必填；发现风险自动挂起高风险处置单 |
| 相近报修汇单 | 同园、同设施或同类别、时间窗内的未结单并入同一处置单；每位报修居民独立留痕、分别收通知、各查各的进度 |
| 高风险只关受影响区域 | 按分区（zone）封闭，其他区域继续开放；围挡安装/拆除与封闭/重开同事务 |
| 维修后异员复检 | 维修人不得复检自己的工作；复检不过退回返工；通过才解除风险 |
| 重新开放不得早于风险解除 | 重开时刻必须 ≥ 复检通过时刻，随后自动撤围挡、结工单 |
| 分段支付 | 共建预算随确认工程量分段申请、审批后入账；幂等键防重复支付 |
| 返工、撤销、质保追偿 | 原付款台账永久保留，另立调整单（负数入账）并关联原台账 |
| 企业移交养护 | 登记移交并新生效养护责任版本；此前承诺与质保责任不消灭，追偿仍向原企业 |
| 跨停机一致 | 围挡、待修工单、付款审批与通知在同一 SQLite 事务提交；通知走事务发件箱，重启后继续投递（至少一次） |
| 街道看板 | 当前可用区域、下一次巡检、未兑现承诺、资金占用（已付净额+在途审批占用） |
| 争议回溯 | `history_on(park, date)` 复原指定日期：为何封闭、谁接管维修、当时居民已收到的通知 |

## 业务约束

- 地块移交：权属与移交记录生效区间化，历史可查
- 设施责任：责任在巡检任务生成时快照，养护移交不回溯改写
- 风险分区：只封闭受影响分区，未复检通过不得开放
- 巡检周期：类别化周期，每日算单、逾期标记、漏跑补算
- 质保追偿：原付款不抹除，调整单另行登记，责任不随移交消失
- 公众通知：受理、并单、派单、封闭、复检、重开、结案逐节点入发件箱

`contracts/context.schema.json` 描述资料结构，`fixtures/context.json` 提供不含真实身份信息的示例，
`src/park_context.py` 负责读取和校验这些资料；`tests/test_park_service.py` 以一座全龄友好口袋公园
端到端覆盖上述全部规则。

## 开发命令

运行测试：

```bash
python3 -m unittest discover -s tests -v
```

编译检查：

```bash
python3 -m compileall -q src
```

两条命令只读写仓库内文件（跨停机测试在临时目录创建 SQLite 库），不需要连接外部业务系统。
